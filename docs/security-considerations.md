# Security Considerations

## 1. Residual contamination

Residual reuse can amplify errors, adversarial inputs, false
assumptions, or outdated information.

A residual must never be treated as trustworthy merely because it was
generated by an internal AI process.

## 2. No automatic reuse

An Inference Residual Record is an observation record.

It is not:

- a reuse authorization,
- an execution instruction,
- a safety certification,
- an audit result,
- a royalty settlement.

A separate classification and authorization process is required before
reuse.

## 3. High-risk residuals

Residuals with a potential hazard of high or critical must:

- be quarantined,
- be marked ineligible for reuse,
- require human review,
- include a quarantine reason.

## 4. Restricted content

Restricted information must not be stored as inline text.

The record should instead contain a protected external reference, such
as an isolated object URI or controlled artifact identifier.

## 5. Secrets

Residuals containing credentials, private keys, authentication tokens,
or other secrets must not use inline content storage.

Secret material should be removed, redacted, rotated, or stored in an
authorized secret-management system.

## 6. Integrity

Every residual record must include a cryptographic digest.

The digest protects against accidental or unauthorized modification of
the referenced residual content.

Supported algorithms in v0.1:

- SHA-256
- SHA-512

## 7. Retention

Residuals should not be retained indefinitely by default.

The retention policy should specify:

- operational class,
- review timing,
- expiration timing,
- legal hold status.

## 8. Self-contamination risk

A regenerative system can become self-contaminating when it repeatedly
reintroduces its own incorrect outputs.

Future versions must therefore control:

- maximum cycle depth,
- provenance continuity,
- confidence degradation,
- model-to-model contamination,
- unresolved audit findings,
- hazardous residual reintroduction.
